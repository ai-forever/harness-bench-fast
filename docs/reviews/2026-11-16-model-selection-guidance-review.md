## 2. Стоимость — правильно ли, и какие/зачем столбцы

### 2.1. Как считается `Cost/solved`
`cost_per_solved = cost_rub / passed` (округление до 2 знаков). Числитель `cost_rub` — **не одно
и то же для разных строк**:

- **премиум-модели** (`Claude`, `GPT-5.5`, `GigaChat 3 Pro`, `GPT-OSS-120B`, `MiniMax`, `GLM-5.2`):
  `cost_rub` переопределяется **фактом биллинга провайдера** из сайдкара `results/reconciled/*`
  (`fork_ladder_override.apply`);
- **прочие** — берётся `summary.estimated_cost_rub` (**оценка по тарифу**).

Пример: `pi_shotlist_sonnet45_20261114` в JSON имеет `estimated_cost_rub = 1195.29` (→ 23.4 ₽/реш.),
но на странице **20.79 ₽** — сработал биллинговый override. Значит столбец «Cost/solved»
**смешивает факт и оценку в одной колонке** и в одних тирах/Парето.

**Последствия:** хедлайновое «premium ≈25× дороже» частично методологический артефакт (факт vs
оценка). Также `cost_per_solved` **включает переплату за проваленные задачи** (это допустимо, но
на странице не сказано).

### 2.2. Что не так со столбцами (по одному)

1. **`Result` (52/52) и `%` (100.0%)** — `%` полностью выводится из `Result`; **дублирование**.
2. **`Reasoning`** дублирует `(thinking: …)` внутри `Model` (напр. «DeepSeek-V4.1-Flash (thinking: medium)» + «medium»).
3. **`Pareto ✅/—`** — символ `—` переиспользуется и для «не Pareto», и для «нет данных» (Harness `—`, Model `—`, Reasoning `—`). Двусмысленно + emoji без текстовой альтернативы (a11y).
4. **`Tier` не показан вообще**, хотя `build_rows` его считает (`Default`/`Balanced`/`Premium`, ровно 24/24/24) и легенда p33/p66 (12.87/49.47 ₽) выводится. Читатель видит легенду тиров, но **не видит тиры**. Обещанная в ADR сущность не доставлена.
5. **`Stem`** (`oc_shotlist_ds41flash_medium_20261107`) — внутренний id; при этом в репозитории есть
   `fork-detail-<stem>.html` — **не слинкован** (упущенный drill-down).
6. **Нет `basis`** (billing/estimate) и **нет абсолютного `cost_rub`** за прогон — видно только удельное значение.
7. **`time_min` и `steps`** посчитаны и лежат в `model-selection-matrix.json`, но на странице **не показаны** (нет «мин/реш.» и «шагов/реш.», хотя методология упоминает время/шаги).
8. **`coverage.full` / `coverage.version`** — есть в данных, на странице не отражены (частичное покрытие видно только косвенно).
9. **Формат чисел:** `55280.97₽` без разрядов рядом с `1.07₽` — плохо читается.

## 3. Найденные дефекты (severity)

### D1 — HIGH. `Tier` вычисляется, но не отображается
`build_rows()` присваивает `r["tier"]`, но ни `render_block()`, ни `render_html()` его не печатают.
Легенда говорит «Тиры — по ₽/решённую задачу (терцили p33/p66)», а столбца/бейджа нет.
Фича из ADR R2 не доставлена на страницу.

### D2 — HIGH. Pareto сравнивает **абсолютный `passed`**, а не долю
Фронт строится по «`passed` ↑, `cost_per_solved` ↓» **внутри бакета**. Но бакет `medium-reflect`
содержит прогоны с **разными знаменателями** (`total ∈ {5, 15, 20}`), а бакеты — с частичным
покрытием. Результат: строка `pi_reflect_ds41flash_20261106` **5/5 = 100%** помечена
**доминируемой** 80–85%-ными строками (16/20, 17/20), т.к. `5 < 17` в абсолютных числах.
Т.е. лучший по качеству прогон показан как «хуже». Это ложный вердикт — ровно то, что страница
должна предотвращать.

### D3 — HIGH. Прогоны с 0 решённых **молча исключаются**
В `build_rows` есть `passed <= 0 → skip` («zero solved (excluded from cost/solved)»). Так
выпадают, напр., `pi_long_ds41flash_20261106`, `oc_medium_long_minimaxm3_off_20261109`,
`pi_medium_long_giga35_low_20261107`, `oc_medium_reflect_giga35base_off_20261113`,
`pi_medium_feasibility_gigachat3pro_20261109` и др. Последствия:
- **негативные результаты невидимы** — страница выглядит лучше реальности (survivorship bias);
- «unmeasured» (не запускали) **смешивается** с «измерено и провалено 0/N»;
- для бакета `long-context` прогоны с 0/6 просто исчезают, а не показываются как провал.

### D4 — MEDIUM. Смешанный базис ₽ в одном столбце/тире/Парето
См. §2.1: биллинг (premium) vs оценка по тарифу (остальные). Без пометки `basis` сравнение
«25×» и тиры несопоставимы по строгости.

### D5 — MEDIUM. Глобальные терцили при разных знаменателях
`p33/p66` считаются по **всем 72 строкам сразу** (shot-list 52, long 6, reflect 5/15/20, Light 391…).
Порог 12.87/49.47 ₽ не сопоставим между бакетами: в `long-context` почти всё окажется «Premium»
просто из-за дорогого знаменателя. Тиры должны считаться **внутри сравнимого подмножества**.

### D6 — MEDIUM. Частичное покрытие участвует в Pareto/тирах
`coverage.full=False` (9 строк) влияет только на anti-patterns и «confidence», но **не исключает**
из Парето/тиров. Асимметрия: анти-паттерны требуют full, фронт — нет.

### D7 — LOW. `dominated_by[0]` — первый по алфавиту, не самый релевантный
Доминант выбирается `sorted(set(...))[0]`, т.е. по имени стема, а не по «самый дешёвый/полный».

### D8 — LOW. Anti-patterns дублируются
Из 34 кандидатов берутся топ-12, где `GPT-5.5 (thinking: off)` ×4, `MiniMax-M3` ×4, `Sonnet 4.6` ×4 — визуальный шум вместо «по одной строке на модель».

### D9 — MEDIUM (infra). Нет CI-гейта дрейфа
`ci.yml` **не запускает** `build_model_selection.py --check/--lint`; `pages.yml` публикует `docs/`
как есть. Значит HTML/md/JSON могут разойтись с `results/*.json` незаметно. У форк-таблиц
(`build_fork_*`) гейты есть — у guidance нет.

## 4. UX-ревью (роль UX-дизайнера)

**Главное:** страница отвечает на «что известно», но **плохо отвечает на «что делать»**.

1. **Шапка без выводов.** Lead — только «на чём построено». Пользователь должен прочитать 72 строки
   и методологию, чтобы понять: *Default = DeepSeek; premium не окупается; выбирай пару
   harness×model; вот пробелы*. Выводы есть в `.md` (TL;DR) → **вынести 3–4 буллета в топ**.
2. **Нет ответа по ситуации.** В `.md` есть «Как читать (по ситуациям)» — на странице нет. Нужен
   короткий «что брать для shot-list / medium / long» + бейдж **«рекомендуем»** на строках-победителях.
3. **Столбец `Bucket` повторяется в каждой строке** (все «Shot List (52)»…) — визуальный шум; лучше
   группировка (подзаголовок/`rowspan`) или анкоры-переходы.
4. **Дубли столбцов** (Result↔%; Reasoning↔Model) — сжать, освободив место под `Tier`, `basis ₽`,
   «мин/реш.».
5. **Нет управления плотным списком** (72 строки): нет фильтра по бакету/harness, сортировки по ₽,
   переключателя «только premium». Просится хотя бы сортировка/анкоры.
6. **Семантика `—` и ✅** — перегрузка (`нет данных` vs `не Pareto`); ✅ без текстовой альтернативы.
7. **Читаемость чисел** — нет разрядов (`55280.97₽`); «%» стоит назвать «pass %».
8. **Доступность/мобайл** — `<table>` без `<caption>`/`scope`, `white-space:nowrap` + 9 колонок →
   горизонтальный скролл на телефоне; зелёный ✅ только символом/цветом.
9. **Drill-down** — `Stem` не кликабелен, хотя есть `fork-detail-<stem>.html`.
10. **Согласованность** — HTML беднее `.md`; стоит держать один источник нарратива (TL;DR + «как читать»).

## 8. Приложение A — Что такое «метрика Парето» (для читателя)

**Идея.** У каждой конфигурации (`харнесс × модель × reasoning`) две характеристики, которые
хочется улучшать одновременно: **качество** (доля решённых задач, `pass_rate`) и **цена**
(`₽ за решённую задачу`). «Лучше» — выше качество **и** ниже цена, но обычно эти цели конфликтуют.

**Доминирование.** Конфигурация `A` **доминирует** `B`, если `A` не хуже `B` по обоим критериям
и строго лучше хотя бы по одному:

```
A ≻ B  ⟺  pass_rate(A) ≥ pass_rate(B)  И  cost/solved(A) ≤ cost/solved(B)
           и хотя бы одно из неравенств строгое
```

Тогда `B` «переплачивает без выигрыша» — брать его незачем (это и есть **anti‑pattern**).

**Фронт Парето (метрика Парето).** Множество **недоминируемых** конфигураций — «лучшие
компромиссы»: ни одну нельзя улучшить по одному критерию, не ухудшив другой. На странице они
помечены ✅; точки вне фронта — доминируемые.

**Почему это важно.** Фронт превращает «мне кажется, модель X лучше» в проверяемое утверждение:
если дорогая модель **не** на фронте — она доминируема более дешёвой с тем же/лучшим качеством.

**Мини‑пример.** Три точки: `A = 80% / 2₽`, `B = 85% / 3₽`, `C = 80% / 5₽`. Итог: `A ≻ C`
(то же качество, дешевле), `B ≻ C` (лучше качество, дешевле). Фронт = {A, B}; `C` — anti‑pattern.

**Где метрика ломается на текущих данных (и почему это правится в v2):**

1. Качество бралось как **абсолютное число** решённых (`passed`), а не доля. Если у прогонов разные
   наборы (5 задач vs 20), «5» и «17» несопоставимы → прогон **5/5 = 100%** ошибочно помечался
   доминируемым **85%‑м** (17/20). Правильно — сравнивать **`pass_rate`** и только внутри одного набора.
2. Часть прогонов с **0 решённых** молча скрыта → фронт «смотрит только на выживших».
3. Фронт считался «внутри бакета», но бакет может **смешивать разные знаменатели** → нужно
   «внутри бакета **и** одного набора/task‑set версии».

**Формула (принято в v2):** сравнивать по `pass_rate` **и только при** `total(A) = total(B)`
(один и тот же набор и версия); `passed` — только для отображения `x/y`.
