# Model & Harness Selection Guidance — план исследования

> Ветка: `research/model-selection-guidance`. Отдельная ветка, чтобы не трогать `main`
> до апрува. Автор: project-a-agent, 2026-11-15.

## 1. Проблема

Пользователи выбирают модель/харнесс **без обоснования**: часто берут дорогие модели
(Opus/Fable) там, где дешёвая (DeepSeek-Flash / GLM-Flash / GigaChat) даёт тот же результат.
У нас уже ~120 прогонов, но нет **слоя рекомендаций** «что × чем × когда использовать».
Нужно превратить сырые результаты в **evidence-based** руководство и правило маршрутизации.

## 2. Что уже есть (инвентарь)

- **120** `results/*.json`, **144** HTML-страницы в `docs/`.
- **Харнессы:** Pi (53), OpenClaw (56), Hermes (5), DeepSeek Harness (4), Wave 19 (1).
- **Наборы:** Shot List (52) · Medium (392–471; полный 90 + семпл 66) · Light (391) · Wave 19 (40).
- **Модели:** DeepSeek-V4.1-Flash · GLM-5.2/5.3 · Claude (Sonnet 4.5/4.6, Opus 4.8/5.5,
  Fable 5/5.1) · GigaChat 3 / 3.5 / 3.5-432B · GPT-5.5 · GPT-OSS-120B · MiniMax-M3 ·
  Qwen3.6-35B-A3B — в разных thinking-режимах (off/low/medium/high/ultra).
- **Метрики:** pass-rate, время, шаги, tokens/₽ (для лестницы ₽ = факт биллинга провайдера).

## 3. Чего НЕ покрыто (пробелы, гипотезы)

1. **Нет слоя руководства** вообще — ни «когда что брать», ни anti-patterns.
2. **Нет метрики «₽ на решённую задачу»** (cost-per-solved) и **фронта Парето** (pass vs cost).
3. **Нет разбивки по сложности** (Shot List vs Medium vs long) — смешиваются лёгкие и тяжёлые.
4. **Матрица покрытия неполная:**
   - Light (391) — почти пусто (`—`);
   - часть моделей прогнана только на одном харнессе (нет парных A/B harness×model);
   - DeepSeek Harness и Hermes — мало наборов.
5. **Нет routing policy** для реального использования (связка с OpenClaw Dynamic Routing/Fallbacks).
6. **Нет явного разбора "дорого, но без выигрыша"** — где premium не окупается.

## 4. Задачи исследования

1. **Coverage matrix** — `harness × suite × model × thinking` → present/missing.
2. **Нормализация метрик** — cost-per-solved, time-per-solved, steps; агрегация по модели.
3. **Fronteer Парето** (pass-rate ↑, ₽ ↓) — кто доминирует, кого доминируют.
4. **Сегментация по сложности** — где дешёвые проседают, а premium даёт реальный прирост.
5. **Тировые рекомендации:** Default (дешёвые) · Balanced · Premium (только с обоснованием).
6. **Routing policy** (draft) — правило выбора модели по классу задачи.
7. **Gap-filling backlog** — какие прогоны добить, чтобы выводы были надёжными.
8. **Anti-patterns** — конкретные примеры из данных «переплатили X, выигрыш 0».

## 5. Роль субагента

- **Primary — Benchmark Portfolio Analyst / Model-Selection Advisor** (количественный
  аналитик): инвентарь `results/*.json` → нормализованные метрики → матрица покрытия →
  фронт Парето → таблица рекомендаций.
- **Secondary (2-й проход) — Guidance Writer / FinOps advisor:** превращает анализ в
  user-facing документ + routing policy.
- **QA (обязателен):** независимая проверка цифр против source-JSON; проверка, что
  рекомендации **не overfit** (нет выводов из одиночного прогона); sanity-check ₽.

Модель по умолчанию для субагентов — `deepseek_flash` (до 3 попыток, апгрейд только с апрувом).

## 6. Deliverable

- `docs/model-selection-guidance.md` (+ `.en.md`) — «что × чем × когда».
- Машиночитаемая `docs/model-selection-matrix.json`.
- Секция «рекомендации» на `docs/fork.html` (по согласованию).
- Бэклог прогонов для закрытия ключевых пробелов.

## 7. Constraints

- Источник истины — `results/*.json`; для ₽ — провайдерский биллинг (dedup-экспорт).
- Никаких выводов из одиночного прогона без явной пометки «низкая уверенность».
- Все изменения — в ветке `research/model-selection-guidance`.
- При автозапуске (5 мин тишины) — **READ-ONLY**: только исследование и план, без кода/правок/деплоя.
