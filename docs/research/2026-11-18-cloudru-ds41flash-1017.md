# Cloud.ru `deepseek-ai/DeepSeek-V4.1-Flash-1017` — что это и как проверить

Дата: 2026-11-18. Ветка: `research/cloudru-ds41flash-1017`.

## Что за модель

В каталоге Cloud.ru (`GET /v1/models`) появилась новая запись
**`deepseek-ai/DeepSeek-V4.1-Flash-1017`** рядом с уже известной
`deepseek-ai/DeepSeek-V4.1-Flash`.

| поле | `…-Flash` | `…-Flash-1017` |
|---|---|---|
| id / name | `deepseek-ai/DeepSeek-V4.1-Flash` | `deepseek-ai/DeepSeek-V4.1-Flash-1017` |

**Вывод:** метаданные, контекст, тариф и лицензия **идентичны**; отличается только
id/name и то, какой build отвечает (`…-1017`). Т.е. `-1017` — это **пин-снапшот
(версионный алиас) той же модели**, замороженный под тегом `1017` (вероятно дата/сборка),
для воспроизводимости. Прямая проба API: обе отвечают и **обе реазонят**
(`reasoning_tokens` > 0), функция-коллинг и structured output одинаковы.

Единственная «аномалия» — при `max_tokens=5` база вернула 36 completion-токенов
(reasoning 32), а `-1017` — 4 (reasoning 0): похоже на разное обращение с
очень маленьким лимитом у снэпшота, не на отсутствие reasoning (при нормальном
лимите обе реазонят).

## Проверка (план)

Прогнать тот же shot-list (52) через **dsh** на `-1017` и сравнить с базой:

1. **Пилот (сделано):** ~8 задач, `thinking: medium`, проверить достижимость через
   dsh/pi-ai (патч `reasoningEfforts` из #30 модель-агностичен → должен работать)
   и качество/токены.
2. **Полный shot-list** на `-1017`: `off` и `medium` (как база) → сравнить
   pass-rate / токены / время / ₽. При желании — `max` (база даёт 52/52).
3. **Учесть в цене:** добавить `-1017` в `~/.openclaw/cloudru-prices.json`
   (refresh каталога) — ставки те же, что у базы.

### Ожидание

- Функционально **та же модель** → ожидаем ≈ тот же результат (51/52 на off/medium,
  52/52 на max), те же токены/время.
- Возможные расхождения — из-за иного build (снэпшот): другой латентный профиль
  или мелкие отличия в sampling; проверяем эмпирически.

## Контролируемая проверка гипотезы «тот же билд» (2026-11-18)

### A. Детерминированные промпты (temp 0), без reasoning_effort
6 промптов → **финальные ответы байт-в-байт совпали у 5/6** (arith, exact_json, primes,
revstr, sumtxt). Расхождение 1/6 (`slugify`) — артефакт `max_tokens=256`: `-1017`
потратил весь бюджет на reasoning и вернул пустой контент.

### B. Контроль детерминизма (одна модель, 3 прогона)
reasoning-токены **недетерминированы и для одной модели** (base 88/98/66;
`-1017` 49/60/85). → по длине reasoning судить о билде **нельзя**.

### C. Пара контролируемых прогонов на бенче (8 задач, `medium`)
- base: **8/8 PASS** (включая `task_263`), `-1017`: **8/8 PASS** (тоже `task_263`).
- Значит `task_263` проходит у **обеих** в контролируемом прогоне → это **флейк**
  базового прогона, а не gap `-1017`.

### D. Скорость и режимы reasoning (`reasoning_effort`, стриминг)
API принимает `reasoning_effort ∈ {none, minimal, low, medium, high, xhigh, ultra, max}`
(**`none`, не `off`**; `off` → 400). Промпт один, 2 повтора на уровень, `max_tokens=1024`:

| уровень | base gen tok/s | 1017 gen tok/s | ответ |
|---|---:|---:|---|
| default | 264 / 147 | 189 / **cap** | оба верны (1017 rep1 усечён) |
| low | 199 / 208 | 130 / 184 | оба верны |
| medium | 85 / 162 | **cap / cap** | base верен; 1017 пусто |
| high | 141 / 210 | **cap / cap** | base верен; 1017 пусто |
| max | 141 / 217 | **cap / cap** | base верен; 1017 пусто |

- **Скорость (tok/s) значимо не отличается** — диапазоны перекрываются
  (медиана base ≈181, `-1017` ≈149; разброс 50–264 у обеих). TTFT 0.8–5 s (шум).
- **Найдено реальное отличие — обращение с `max_tokens`:**
  base **превышает** лимит (completion 1184…2401 при лимите 1024) и всё равно отдаёт
  ответ; `-1017` **жёстко упирается в 1024**, весь бюджет уходит в reasoning,
  **контент пустой** (7 из 10 прогонов, начиная с default/medium).
- `ultra` у `-1017` → HTTP **429** (rate limit) в первом прогоне.

### Вывод (решение): **одна и та же модель**
Каталог/тарифы/контекст/ответы совпадают; `-1017` — **пин-снапшот (версионный алиас)**
той же модели DeepSeek-V4.1-Flash. Наблюдаемое отличие в обращении с `max_tokens`
(base overshoot vs `-1017` hard-cap) — **serving-деталь снэпшота**, а не признак иной
модели (и подтверждаемо только при жёстком лимите). Вопрос закрыт: **модель та же**,
отдельное онбординг/сравнение не требуется. В сравнениях просто задавать щедрый
`max_tokens`.

## Внимание по стоимости

Провайдер тарифицирует **весь prompt по input-ставке** (см. reconciliation:
наши `estimated_cost_rub` занижены ~2.4–3.2×, т.к. cacheRead мы биллим по 6.5,
а провайдер — по 64.94). При оценке пилота/полного прогона это учитывать.
