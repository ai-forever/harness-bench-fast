# chronorule

Внутренняя библиотека календарных правил: гражданские даты без часовых поясов,
производственные календари, рабочие дни и конвенции переноса, отчётные периоды,
длительности, повторения в духе RRULE (RFC 5545, урезанный вариант), расписания
и русские подписи для интерфейса.

Библиотека выросла из сервиса планирования платежей и сервиса расчёта зарплаты.
Многие её решения выглядят странно, но на них завязаны сохранённые расписания,
отчёты и письма клиентам. **Поведение, описанное в JSDoc, — это контракт.** Если
вам кажется, что функция считает «неправильно», сначала найдите её описание:
почти наверняка странность задокументирована и оставлена намеренно.

- Node.js ≥ 18, без зависимостей.
- Точка входа — `src/index.js`. Всё, что экспортирует `index.js`, — публичный API;
  всё остальное (`src/internal.js`, классы `Cal`, `Rule`, вспомогательные функции
  модулей) — внутреннее.
- Тесты: `node test/run.js` (набор на `node:assert`, без фреймворков).

## Основные соглашения

### Даты — это строки

Публичный API принимает и возвращает даты только строками `YYYY-MM-DD` (ровно
четыре цифры года, две — месяца и дня). Объект `Date` не используется нигде:
время суток и часовые пояса к гражданскому календарю отношения не имеют.

- не строка → `E_TYPE`;
- строка другой формы (`2024-5-1`, `2024-05-01T00:00`, пробел в начале) → `E_PARSE`
  (никакой обрезки пробелов — для пользовательского ввода есть `parseDate`);
- форма верная, но даты не существует (`2023-02-29`, `2024-13-01`) → `E_RANGE`;
- поддерживаются годы 1000…9999; результат за пределами → `E_RANGE`.

### Дни недели

Номер дня недели: **понедельник = 0 … воскресенье = 6** (порядок ISO, а не
`Date#getDay()`). Текстовые коды — `MO TU WE TH FR SA SU`, только заглавными.

### Ошибки

Все ошибки — `ChronoError` с полем `code`:

| код | когда |
|-----|-------|
| `E_PARSE` | строка не распознана (форма/синтаксис) |
| `E_RANGE` | форма верная, значение вне диапазона |
| `E_RULE` | любая ошибка в правиле повторения (всегда именно этот код) |
| `E_LIMIT` | вычисление было бы бесконечным или слишком большим |
| `E_TYPE` | неверный тип аргумента, неизвестный ключ объекта |

Порядок проверок аргументов важен, когда ошибок несколько: он описан в JSDoc
функций («Argument checks, in order: …»). По умолчанию аргументы проверяются
слева направо по мере использования.

### Необязательные аргументы

Необязательный календарь передаётся позиционно последним «обычным» аргументом
(`null` — календарь по умолчанию: выходные суббота и воскресенье, праздников нет).
Настройки функции передаются последним аргументом-объектом `options`
(`startOfWeek(date, { weekStart: 'SU' })`). Отсутствующая настройка и настройка со
значением `null` в большинстве функций означают значение по умолчанию; где это не
так, сказано в JSDoc.

## Производственный календарь

```js
const cal = {
  weekend: ['SA', 'SU'],
  holidays: ['2024-05-01', '2024-05-09', '2024-05-10'],
  workdays: ['2024-04-27'],        // перенесённая рабочая суббота
  dayHours: 8,
  preholidayCut: 1,
};
dayKind('2024-05-08', cal);       // 'preholiday' — завтра праздник, день короче на час
dayKind('2024-04-27', cal);       // 'transfer'
workHoursInMonth(2024, 5, cal);   // норма часов за май
```

Статус дня определяется строго по приоритету: праздник → выходной (если дата не
указана в `workdays`) → предпраздничный (если **следующий календарный день** —
праздник из списка) → перенесённый рабочий → обычный рабочий. Праздники,
выпавшие на выходные, автоматически не переносятся — переносы должны быть явно
перечислены в спецификации, как в постановлении правительства. Подробности —
в `src/calendar.js`.

## Рабочие дни и конвенции переноса

`addBusinessDays`, `businessDaysBetween`, `workHoursBetween` используют *разные*
соглашения о границах интервалов — так исторически сложилось в сервисе
зарплаты, и на это завязаны отчёты. `businessDaysBetween` считает полуинтервал
(start, end], а `workHoursBetween` — отрезок [start, end]. См. `src/business.js`.

Конвенции переноса (`roll`) — строки с подчёркиваниями: `none`, `following`,
`preceding`, `modified_following`, `modified_preceding`, `nearest`. Они хранятся
в базе и **не переименовываются** ни в каком порте.

## Повторения и расписания

```js
expandRRule('FREQ=MONTHLY;BYDAY=-1FR;COUNT=3', '2024-01-01');
// ['2024-01-26', '2024-02-23', '2024-03-29']

scheduleBetween({
  rule: 'FREQ=MONTHLY;BYMONTHDAY=25',
  start: '2024-01-01',
  exdates: ['2024-05-25'],
  roll: 'following',
  calendar: cal,
}, '2024-01-01', '2024-12-31');
```

В отличие от RFC 5545 дата начала **не** считается первым повторением, если не
подходит под правило. Ежемесячное правило, начатое 31-го, срабатывает только в
месяцах, где есть 31-е число (без «переполнения», в отличие от `addMonths`).
Исключения (`exdates`) сравниваются с датами **до** переноса. Подробное описание
алгоритма развёртки — в комментарии к разделу «Expansion» файла `src/rrule.js`,
описание конвейера расписания — в `src/schedule.js`.

## Длительности и месяцы

`addMonths` повторяет поведение `Date.prototype.setMonth`: несуществующий день
«переливается» в следующий месяц (`addMonths('2024-01-31', 1) === '2024-03-02'`).
`addMonthsClamped` прижимает к концу месяца. `addDuration` использует переливание,
`diffDates` — прижатие; они намеренно не обратны друг другу. См. `src/civil.js`
и `src/duration.js`.

## Отчётные периоды

Метки: `2024`, `2024-H1`, `2024-Q3`, `2024-05`, `2024-W05` (ISO-неделя, год —
ISO-год недели), `FY2025`. Финансовый год называется по календарному году,
**в котором он заканчивается**; месяц начала задаётся настройкой `fiscalStart`.

## Форматирование и подписи

`formatDate(date, pattern)` понимает токены из таблицы в `src/format.js`
(самый длинный токен выигрывает, текст в `[квадратных скобках]` выводится как
есть). Все подписи в `src/humanize.js` собираются по жёстким правилам, без
системной локали, и сравниваются в тестах посимвольно — включая «ё», пробелы,
запятые и длинное тире `–` (U+2013) в `formatRange`.

## Порт на Python

Для аналитиков и ETL нужен порт библиотеки на Python с **тем же поведением**.
Порт — пакет `chronorule/` (каталог в корне репозитория рядом с `src/`),
только стандартная библиотека, Python ≥ 3.9. Правила соответствия:

### Имена

1. Все имена, экспортируемые из `src/index.js`, доступны на верхнем уровне
   пакета: `from chronorule import add_months, ChronoError`.
2. Имена функций переводятся из camelCase в snake_case: перед каждой заглавной
   буквой ставится `_`, буква становится строчной (`addMonthsClamped` →
   `add_months_clamped`, `isoWeek` → `iso_week`, `nthWeekdayOfMonth` →
   `nth_weekday_of_month`).
3. Исключения из правила 2 (сложились исторически, в Python-коде аналитиков
   используются именно такие имена):

   | JavaScript | Python |
   |------------|--------|
   | `parseRRule` | `parse_rule` |
   | `stringifyRRule` | `rule_to_string` |
   | `expandRRule` | `expand_rule` |

4. Класс ошибки называется так же — `ChronoError`; это подкласс `ValueError`
   с атрибутом `code` (строка `E_PARSE`, `E_RANGE`, `E_RULE`, `E_LIMIT` или
   `E_TYPE`). Коды ошибок и условия, при которых они возникают, должны
   совпадать с JS-версией.

### Параметры

5. Позиционные параметры остаются позиционными, в том же порядке и с теми же
   значениями по умолчанию (`null` → `None`). Необязательный календарь —
   тоже позиционный: `add_business_days(date, n, calendar=None)`.
6. Последний параметр-объект `options` превращается в **keyword-only**
   аргументы с именами в snake_case: `startOfWeek(date, { weekStart: 'SU' })` →
   `start_of_week(date, week_start="SU")`. Если имя совпадает с ключевым словом
   Python, к нему добавляется подчёркивание: `{ from }` → `from_=`.
7. Ключи простых объектов во входных данных и в результатах тоже переводятся в
   snake_case: спецификация календаря `{ dayHours, preholidayCut }` →
   `{"day_hours": ..., "preholiday_cut": ...}`; результат `dayInfo` содержит
   `is_workday`, результат `weekdayOccurrence` — `from_end`. Ключ, который в
   JS-версии был бы неизвестным, в порте тоже неизвестен (например,
   `dayHours` в Python-спецификации календаря — это ошибка `E_TYPE`).
8. **Строковые значения не меняются**: коды дней недели, названия конвенций
   (`modified_following`), форм (`dative_plural`), видов периодов, частоты
   правил, тексты описаний.

### Типы

9. `null` ↔ `None`, массив ↔ `list`, простой объект ↔ `dict`, строка ↔ `str`,
   `true/false` ↔ `True/False`. Все числа в API целые ↔ `int`; «целое число» в
   проверках типов — это `int`, но не `bool`. Функции возвращают `list`, а не
   кортежи (пара дат из `periodRange` — тоже список из двух строк).
10. Проверка «строка» — `isinstance(x, str)`, «массив» — `list`, «объект» — `dict`.

### Как проверять порт

`tests/vectors_sample.json` — векторы, снятые с JS-версии: вызов функции порта
по Python-имени с аргументами `args` и `kwargs` и ожидаемый итог `expect` —
либо `{"result": <значение>}`, либо `{"error": "<код ChronoError>"}`.
`python3 tests/run_vectors.py` прогоняет их против пакета `chronorule/` и
печатает расхождения. Эти векторы — лишь образец: поведение порта должно
совпадать с JS-версией на любых входах, включая описанные в JSDoc граничные
случаи и ошибки.
