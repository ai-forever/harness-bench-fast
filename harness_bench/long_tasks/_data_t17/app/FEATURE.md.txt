# Доработка «Партии, частичные возвраты, валюты» (SKL-212, SKL-230, SKL-241)

Документ описывает обязательные изменения приложения `stockroom`. Всё, что здесь
сказано, будет проверяться приёмочными тестами — через Python API модулей пакета и
через командную строку `python3 -m stockroom`. Где формулировка допускает выбор, выбор
явно оставлен на усмотрение разработчика («на ваше усмотрение»).

## 0. Общие требования

1. **Обратная совместимость.** Все существующие тесты в `tests/` должны проходить без
   изменений. Существующие функции, их параметры, ключи документов, форматы вывода
   команд и колонки отчётов сохраняются, если ниже явно не сказано иное. Новые
   параметры функций — только необязательные, в конце списка параметров.
2. Товар, у которого не задана валюта и не включён учёт сроков, должен вести себя ровно
   так же, как до доработки: FIFO-расход, рублёвые цены, те же суммы.
3. Только стандартная библиотека Python, совместимость с Python 3.9.
4. Все денежные округления — как в `money.q2` (до копеек, половина — вверх).
5. Ошибки бизнес-логики — исключения из `stockroom.errors` (наследники `StockError`):
   неверные данные — `ValidationError`, нехватка товара — `InsufficientStock`,
   недопустимый статус документа — `DocumentStateError`, отсутствующая сущность —
   `NotFound`, новое — `RateMissing` (раздел 4). В CLI любая такая ошибка печатается в
   stderr как `ошибка: <сообщение>` с кодом возврата 2 (как сейчас). Тексты сообщений
   новых ошибок — на ваше усмотрение.

## 1. Схема базы 4

`db.SCHEMA_VERSION` становится **4**. Новая пустая база и база после миграции содержат
ключ верхнего уровня `"rates": {}` (курсы валют, раздел 4).

Миграция 3 → 4 (выполняется автоматически при `Database.open`, как прежние; цепочка
1 → 2 → 3 → 4 тоже должна работать):

* каждому товару добавляются `"currency": <базовая валюта базы>` (`meta.base_currency`,
  по умолчанию `"RUB"`) и `"track_expiry": false`;
* каждому слою себестоимости (`layers[SKU][i]`) добавляются `"lot": "<doc>-<line>"`
  (например `"R-0001-1"`, `"MIGR-1"`, `"ADJ-0003-1"`) и `"expiry": null`;
* каждому распределению (`allocations`) в строках заказов добавляются `"lot"` по тому
  же правилу (`"<doc>-<line>"` распределения) и `"expiry": null`;
* строки документов прихода **не** меняются;
* `"schema": 4`.

Как и раньше, исходный файл не перезаписывается до первого `save()`.

## 2. Партии и сроки годности

### 2.1. Карточка товара

Новое поле `track_expiry` (bool, по умолчанию `false`) — учёт сроков годности.

* `catalog.addItem(..., currency=None, track_expiry=False)` — `currency` см. раздел 4.2;
* `catalog.updateItem(db, sku, track_expiry=...)` — поле можно менять; значения,
  которые надо принимать в `track_expiry` (и в CSV, и в `updateItem`): `True/False`,
  строки `1/0`, `true/false`, `yes/no`, `да/нет` (без учёта регистра); прочее —
  `ValidationError`.
* CLI: `item add ... --track-expiry` (флаг), `item update SKU --track-expiry yes|no`.
* `item show` печатает после всех прежних строк (и после строки о скидках за
  количество, если она есть) две новые строки:
  `Валюта цены: RUB` (код валюты товара) и `Учёт сроков годности: да` / `нет`.

### 2.2. Партия

Партия — это слой себестоимости (`layers[SKU]`), который создаёт строка прихода. У
партии есть код `lot` и срок годности `expiry` (ISO-дата или `null`). Код партии
задаётся в строке прихода; если не задан — код по умолчанию `"<номер прихода>-<номер
строки>"`, например `"R-0007-2"` (строки нумеруются с 1 в порядке документа).
Существующие ключи слоя (`doc`, `line`, `date`, `qty`, `cost`) сохраняют смысл,
`costing.layers_for` продолжает их возвращать (плюс новые ключи).

Партии, созданные не приходом: излишек инвентаризации (`adjust_count`) — партия с
кодом, равным номеру документа (`"ADJ-0001"`), без срока годности; партии миграции —
раздел 1.

### 2.3. Строка прихода

Синтаксис строки в CLI и в `receiving.parse_line` расширяется:

    SKU:КОЛ-ВО@ЦЕНА[#ПАРТИЯ][!СРОК]

например `YOG:10@31.5`, `YOG:10@31.5#L-0314`, `YOG:10@31.5!2024-04-01`,
`YOG:10@31.5#L-0314!2024-04-01`. Порядок необязательных частей — именно такой:
сначала `#`, потом `!`. `parse_line` возвращает словарь с ключами `sku`, `qty`,
`cost` и дополнительно `lot` и/или `expiry` — только если они указаны в строке.
`receiving.receive` принимает и строки, и словари с необязательными ключами `lot`,
`expiry`.

Проверки строки прихода (каждое нарушение — `ValidationError`, приход не проводится
целиком; проверки прежних полей — как раньше):

* код партии — от 1 до 20 символов из `A-Z a-z 0-9 _ . -` (регистр сохраняется);
* код партии уникален в пределах товара: он не должен совпадать ни с кодом партии,
  которая сейчас есть в слоях этого товара, ни с кодом партии любой строки проведённого
  (не сторнированного) прихода этого товара (с учётом кодов по умолчанию), ни с кодом
  другой строки этого же прихода для того же товара;
* срок годности — дата (ISO или ДД.ММ.ГГГГ, хранится в ISO);
* для товара с `track_expiry = true` срок **обязателен**; для товара без учёта сроков
  срок указывать **нельзя**;
* срок годности не может быть раньше даты прихода (равен — можно).

В строке документа прихода (`documents["R-…"]["lines"][i]`) ключи `lot` и `expiry`
появляются **только если заданы явно** (у строк без них документ выглядит, как раньше).

### 2.4. Порядок расхода: FEFO

Любой расход товара (отгрузка заказа, списание, недостача инвентаризации) забирает
количество из партий в порядке FEFO:

1. сначала партии со сроком годности — по возрастанию срока;
2. затем партии без срока;
3. при равных сроках (и среди партий без срока) — по дате прихода партии, затем по
   номеру документа, затем по номеру строки (то есть как прежний FIFO).

Для товаров без сроков годности это в точности прежний FIFO.

**Отгрузка** (`orders.ship_order`) не использует партии, срок годности которых
**раньше даты отгрузки** (партия со сроком, равным дате отгрузки, отгружается).
Проверка «всё или ничего» учитывает только непросроченные партии: если их не
хватает, бросается `InsufficientStock` с `need` — требуемым количеством и `have` —
количеством в непросроченных партиях (строки, как в `qty_str`), и ничего не списывается.

**Списание** (`adjustments.writeoff`) и **недостача** при инвентаризации
(`adjustments.adjust_count`) используют все партии, включая просроченные, в порядке
FEFO. Новый необязательный параметр `adjustments.writeoff(db, sku, qty, date, reason,
lot=None)`: если `lot` задан, списывать только из этой партии; если такой партии у
товара нет (в текущих слоях) — `ValidationError`; если в ней не хватает —
`InsufficientStock`. CLI: `writeoff SKU QTY --date D --reason R [--lot LOT]`.

Распределения в строках отгруженного заказа (`allocations`) дополнительно содержат
ключи `"lot"` и `"expiry"` партии. Прежние ключи и их смысл сохраняются. Документ
списания (`WO-…`) хранит распределения в том же формате.

### 2.5. Просмотр партий: `stockroom/lots.py` (новый модуль)

* `lots.lots_of(db, sku)` → список партий товара **с ненулевым остатком** в порядке
  FEFO (раздел 2.4), каждая — словарь
  `{"lot": str, "expiry": str|None, "qty": Decimal, "cost": Decimal, "doc": str, "date": str}`,
  где `cost` — цена единицы партии в рублях, `doc`/`date` — документ и дата партии.
  Неизвестный товар — `NotFound`.
* `lots.expiring(db, on_date, days=30)` → партии всех товаров с ненулевым остатком и
  сроком годности **не позже** `on_date + days` дней (включая уже просроченные);
  словари `{"sku", "name", "lot", "expiry", "qty": Decimal, "days_left": int}`, где
  `days_left` = (expiry − on_date) в днях (отрицательно для просроченных).
  Сортировка — по `expiry`, затем `sku`, затем `lot`.

CLI:

* `lots SKU` — таблица партий товара (порядок — как в `lots_of`), колонки с ключами
  `lot`, `expiry`, `qty`, `cost` (заголовки текстовой таблицы — на ваше усмотрение). В
  режиме `--format csv` первая строка — `lot,expiry,qty,cost`, значения «сырые»: срок
  в ISO или пусто, количество как в `qty_str` (`12`, `2.5`), цена с двумя знаками
  (`30.00`).
* `report expiry --on ДАТА [--days N]` (по умолчанию 30) — новый отчёт в
  `reports.REPORTS["expiry"]`, модуль `reports/expiry.py` с `build(db, on_date,
  days=30)` (строки = `lots.expiring`) и `render(...)`; колонки (и заголовок CSV):
  `sku,name,lot,expiry,qty,days_left`. Без `--on` — ошибка (код 2).

### 2.6. Экспорт и импорт

* `csvio.export_lots(db, path)` и `export lots FILE` — все партии с ненулевым остатком:
  товары по возрастанию артикула, внутри товара — FEFO; колонки
  `sku,lot,expiry,qty,cost,currency,cost_cur` (`currency`/`cost_cur` — раздел 4.4, пусто
  для рублёвых партий; `expiry` пусто, если срока нет). Возвращает число строк.
  Сообщение CLI — как у прочих выгрузок.
* `csvio.import_stock` принимает необязательные колонки `lot` и `expiry` (пустое
  значение — не задано). Правила проверки — как у прихода (2.3); ошибка любой строки —
  ничего не загружается (как сейчас).
* `csvio.import_items` принимает необязательные колонки `currency` и `track_expiry`
  (пусто — значения по умолчанию).
* `csvio.export_items` дописывает в конец колонки `currency` и `track_expiry`
  (`csvio.ITEM_COLUMNS` = прежние колонки + эти две); `track_expiry` пишется как `1`/`0`.
  Файл, выгруженный `export_items`, должен загружаться `import_items` без ошибок.

## 3. Частичные возвраты

### 3.1. API

    returns.return_order(db, order_id, date, reason=None, lines=None)

* `lines=None` — вернуть **всё, что ещё не возвращено** по заказу (для заказа без
  прежних возвратов это прежний полный возврат, результат должен совпадать с прежним).
* `lines` — список строк `"SKU:КОЛ-ВО"` (синтаксис как у строк заказа) или словарей
  `{"sku", "qty"}`. Одинаковые артикулы складываются.

Проверки (порядок: статус заказа, дата, строки):

* заказ в статусе `returned` — `DocumentStateError` (как сейчас); вернуть можно заказ в
  статусе `shipped` или `partially_returned`, иначе `DocumentStateError`;
* дата возврата раньше даты отгрузки — `DocumentStateError` (как сейчас);
* артикула нет в заказе — `ValidationError`; количество ≤ 0 или не число —
  `ValidationError`; количество больше, чем «отгружено минус уже возвращено» по этому
  артикулу, — `ValidationError`. При любой ошибке ничего не меняется.

### 3.2. Что происходит при возврате

* Товар возвращается **в те партии, из которых был отгружен**, начиная с последнего
  распределения строки заказа (обратный порядок отгрузки): из последнего
  распределения возвращается сколько можно (его количество минус уже возвращённое из
  него), затем из предыдущего и т. д. Если слоя партии уже нет, он восстанавливается с
  прежними документом, строкой, датой, ценой, кодом партии и сроком. Остаток товара
  увеличивается, инвариант `check_integrity()` сохраняется.
* Сколько возвращено из каждого распределения, хранится в самом распределении
  строки заказа, ключ `"returned"` (строка-количество). Распределения без этого ключа
  считаются невозвращёнными.
* По каждому возвращаемому артикулу — одно движение `return` с количеством возврата и
  себестоимостью = сумма (количество × цена партии) по восстановленным частям,
  округлённая до копеек.
* Документ возврата `RT-…` — как сейчас, строки `{"sku", "qty", "cost"}` (ровно эти
  ключи) в порядке строк заказа; `cost` — себестоимость строки возврата. Дополнительные
  ключи документа (например, какие партии восстановлены) — на ваше усмотрение.
* **Сумма к возврату** `amount` (с НДС) считается по строкам возврата: цена единицы —
  та же, что в заказе: `pricing.unit_price` на **дату заказа**, со скидкой за
  количество **по количеству строки заказа** (а не по возвращаемому количеству), с
  ценовой группой и скидкой покупателя; сумма строки без НДС = q2(цена × возвращаемое
  количество), НДС = q2(сумма × ставка / 100); `amount` = сумма (без НДС + НДС) по
  строкам. Для возврата всего заказа одним документом это равно `order_amounts` (как
  сейчас).
* Статус заказа после возврата: `returned`, если по всем строкам возвращено всё
  отгруженное, иначе `partially_returned`. В заказе `return_doc` — номер последнего
  возврата (как сейчас для полного), `returns` — список номеров всех возвратов по
  порядку.
* `returns.returns_for(db, order_id)` возвращает все возвраты заказа (по номеру).

### 3.3. Влияние на другие части

* Отчёт о продажах (`reports/sales.py`): заказы в статусе `partially_returned`
  учитываются как отгруженные; каждый возврат (в т. ч. частичный) уменьшает в периоде
  своей даты количество, себестоимость (на `cost` строк возврата) и выручку — на сумму
  **без НДС** строк возврата, посчитанную по правилу 3.2 (цена строки заказа).
* Взаиморасчёты (`payments.ledger/balance`) и акт сверки учитывают возврат суммой
  `amount` (как сейчас).
* Накладная (`waybill`) печатается и для заказа в статусе `partially_returned`.
* `order show`: текст статуса `partially_returned` — `частично возвращён`.
* CLI: `return ORDER [SKU:КОЛ-ВО ...] --date D [--reason R]` — без строк возвращается всё
  оставшееся. Сообщение — прежнее: `Возврат RT-0002 по заказу S-0001 оформлен, к
  возврату 1 234,50`.

## 4. Валюты

### 4.1. Курсы: `stockroom/rates.py` (новый модуль)

Курс — сколько рублей (базовой валюты) стоит 1 единица валюты. Хранение:
`db.data["rates"] = {"USD": [{"date": "2024-03-01", "rate": "91.2500"}, ...]}` — по
каждой валюте список по возрастанию даты, курс строкой с **4 знаками** после запятой.

* `rates.set_rate(db, currency, date, rate)` — задать курс на дату; возвращает курс
  (Decimal, 4 знака, округление половины вверх). Код валюты — три латинские буквы
  (регистр входа не важен, хранится заглавными); курс > 0; дата — как везде. Курс на
  уже заданную дату заменяется. Курс базовой валюты задавать нельзя. Нарушения —
  `ValidationError`.
* `rates.get_rate(db, currency, date=None)` → Decimal: курс с **самой поздней датой, не
  позже** `date`. Для базовой валюты — `1` (без обращения к таблице). Если подходящего
  курса нет (валюта неизвестна или все курсы позже даты) — `errors.RateMissing`
  (новый класс, наследник `StockError`). `date=None` — последний известный курс.
* `rates.convert(db, amount, currency, date=None)` → q2(amount × get_rate(...)).
* `rates.list_rates(db, currency=None)` → `[{"currency", "date", "rate": Decimal}]` по
  валюте, затем по дате.

CLI:

* `rate set ВАЛЮТА ДАТА КУРС` → `Курс USD на 2024-03-01: 91,2500` (дата — как введена
  в команде, курс — 4 знака с запятой);
* `rate show ВАЛЮТА [--date ДАТА]` → `Курс USD на 2024-03-05: 91,2500 (от 2024-03-01)`
  (в скобках — дата найденного курса); без `--date` вместо даты печатается
  `последнюю дату`;
* `rate list [ВАЛЮТА]` — таблица, колонки (и заголовок CSV) `currency,date,rate`.

### 4.2. Валюта цены товара

Новое поле карточки `currency` — валюта цены продажи `price` (по умолчанию базовая).
`catalog.addItem(..., currency=...)`, `updateItem(currency=...)`, CLI `item add/update
--currency USD`. Проверка кода — как в 4.1 (`ValidationError`). Курс на момент
заведения карточки не требуется.

### 4.3. Продажи в валюте: пересчёт по курсу на дату заказа

Если цена товара в иностранной валюте, **первым шагом** правил цены (до оптовой
скидки, скидки за количество и скидки покупателя) она пересчитывается в рубли:
`q2(price × get_rate(валюта, дата))`, где дата — **дата заказа**. Дальше всё как прежде
(все суммы — в рублях). Курса нет — `RateMissing`.

Это правило обязано действовать **везде, где считаются цены продажи**:

* `pricing.unit_price / line_amounts / order_amounts / order_total` (параметр `date` —
  дата курса; `order_amounts` передаёт дату заказа);
* счёт (`documents/invoice.py`: `invoice_data` и `render_invoice`);
* отчёт о продажах (`reports/sales.py`) — и отгрузки, и возвраты (курс — на дату заказа);
* суммы возвратов (раздел 3.2) — через цену на дату заказа;
* `pricing.price_list(db, customer, qty=1, date=None)` — новый необязательный параметр
  `date`; `None` — последний известный курс;
* ценники (`labels.py`) — по последнему известному курсу (цена пересчитывается в
  рубли так же — q2 — до скидки за количество и НДС).

Для рублёвых товаров ничего не меняется.

### 4.4. Приход в валюте

`receiving.receive(db, supplier, date, lines, note=None, currency=None)`; CLI
`receive --currency USD ...`. Цены строк (`cost`) задаются в валюте документа.

* Курс — `get_rate(валюта, дата прихода)`; нет курса — `RateMissing`, приход не
  проводится.
* Цена единицы партии в рублях (`cost` слоя) = q2(цена × курс). У такой партии в слое
  дополнительно `"currency": "USD"` и `"cost_cur"` — цена в валюте (строка с 2 знаками).
* Движение `in` — себестоимость q2(количество × рублёвая цена единицы).
* Документ прихода: строки хранят цену **в валюте документа**; `total` — сумма в
  рублях (сумма по строкам q2(количество × рублёвая цена)); дополнительно
  `"currency"`, `"rate"` (строка с 4 знаками) и `"total_cur"` — сумма в валюте (сумма по
  строкам q2(количество × цена)). У рублёвых приходов этих трёх ключей нет.
* Сообщение CLI для валютного прихода: к прежнему тексту дописывается
  ` (<total_cur> <ВАЛЮТА>)`, например
  `Приход R-0003 проведён: строк 1, сумма 8 360,16 (85,20 EUR)`.
* Отчёт о закупках, себестоимость отгрузок и списаний — в рублях (по `cost` слоёв).

### 4.5. Оценка остатков

`reports/valuation.py`: колонки и смысл прежние; стоимость валютных партий — по
исторической рублёвой цене партии (курс на дату прихода), то есть просто по `cost`
слоёв. Новый необязательный параметр `build(db, category=None, revalue=None)` (и
`total(db, category=None, revalue=None)`, CLI `report valuation --revalue ДАТА`):
если задан, **валютные** партии оцениваются по цене единицы q2(cost_cur × курс на дату
`revalue`), рублёвые — как обычно; value строки = q2(сумма количество × цена единицы по
партиям), avg_cost = q2(value / qty).

## 6. Примеры

База из `tests/helpers.make_db()`; дополнительно:

    catalog.addItem(db, "YOG", "Йогурт", "60", vat="10", track_expiry=True)
    catalog.addItem(db, "WINE", "Вино", "12.50", vat="20", currency="EUR")
    rates.set_rate(db, "EUR", "2024-03-01", "98.1234")
    rates.set_rate(db, "EUR", "2024-03-10", "101.5")
    receiving.receive(db, "SUP1", "2024-03-02",
                      ["YOG:10@30#A!2024-03-20", "YOG:10@31#B!2024-03-15", "YOG:5@29!2024-03-25"])
    receiving.receive(db, "SUP2", "2024-03-05", ["WINE:12@7.10"], currency="EUR")

* `lots.lots_of(db, "YOG")` — партии `B` (до 15.03), `A` (до 20.03), `R-0003-3` (до 25.03).
* Приход вина: курс 98,1234 (от 01.03), цена партии 696,68 руб., `total` = 8360.16,
  `total_cur` = 85.20.
* Заказ C2 от 2024-03-16 на `YOG:12`, `WINE:3`, отгрузка 16.03: партия `B` просрочена и
  не берётся, отгружается 10 из `A` и 2 из `R-0003-3`. Цена вина — по курсу 101,5 (от
  10.03): 12,50 → 1 268,75 → опт (−10 %) 1 141,88 → скидка C2 (−5 %) 1 084,79.
* Частичный возврат `YOG:3` от 17.03: 2 шт. возвращаются в `R-0003-3`, 1 шт. — в `A`;
  статус заказа `partially_returned`; `amount` = 169.29 (цена йогурта 51,30 × 3 =
  153,90 + НДС 15,39).
