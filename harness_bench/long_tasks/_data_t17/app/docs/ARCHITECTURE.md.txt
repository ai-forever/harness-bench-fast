# Устройство stockroom

## Слои

```
cli.py                     разбор аргументов, вывод; каждая команда — функция cmd_*(args, db)
  │
  ├── бизнес-операции      catalog, partners, receiving, orders, returns, adjustments,
  │                        purchasing, payments, stocktake, kits, price_history
  ├── расчёты              pricing (цены продажи), costing (себестоимость, FIFO-слои),
  │                        inventory (остатки)
  ├── печатные формы       documents/invoice, waybill, receipt_note, act
  ├── отчёты               reports/* (build → строки, render → текст/CSV)
  ├── обмен                csvio, importers/onec, integrations/marketplace, integrations/accounting
  └── хранилище            db (JSON-файл, атомарная запись), migrations (схемы 1→2→3)
```

Бизнес-операции работают прямо со словарём `db.data` и сами отвечают за
согласованность: остаток (`stock`) и FIFO-слои (`layers`) меняются вместе, движение
(`movements`) пишется на каждое изменение остатка, в журнал аудита — запись на каждую
операцию. База сохраняется только в `cli.main` (или явно `db.save()` в скриптах).

## Данные

Все количества и деньги хранятся **строками** и обрабатываются как `Decimal`
(`money.D`). Округление денег — `money.q2` (до копеек, половина вверх), количества
хранятся без лишних нулей (`money.qty_str`). Даты — строки ISO `YYYY-MM-DD`.

Номера документов выдаёт `ids.next_id` по префиксам: `R` (приход), `S` (заказ), `RT`
(возврат), `ADJ` (инвентаризация), `WO` (списание), `PO` (заказ поставщику), `PAY`
(оплата), `KIT` (сборка), `MV` (движения, 6 знаков).

### Себестоимость

Каждая строка прихода создаёт FIFO-слой `{doc, line, date, qty, cost}` (цена за
единицу). Любой расход (отгрузка, списание, недостача, сборка комплекта) забирает
количество из самых старых слоёв (`costing.consume_fifo`) и возвращает
«распределения» — из каких слоёв сколько взято. Распределения сохраняются в строке
заказа (`allocations`): по ним печатается накладная и выполняется возврат (товар
возвращается в те же слои, `costing.restore`).

Инвариант: сумма `qty` слоёв товара равна его остатку (`Database.check_integrity`,
команда `check`).

### Цены продажи

Правила — в docstring `pricing.py`: базовая цена карточки → оптовая скидка (группа
`wholesale`) → скидка за количество (`price_breaks`) → персональная скидка покупателя,
с округлением до копеек после каждого шага; НДС считается от суммы строки.

Исторически эта логика **продублирована**: `documents/invoice.py` (счёт, 2020 г.) и
`reports/sales.py` (отчёт о продажах, ради скорости) считают цены сами. Совпадение с
`pricing.py` проверяют тесты `InvoiceMatchesPricingTest` и `SalesMatchesPricingTest`.
Прочие места (`payments`, `returns`, `integrations`, `labels`, `order show`) пользуются
`pricing.py`.

Цена в заказе не фиксируется: суммы пересчитываются по текущей карточке товара при
каждом обращении. История цен (`price_history.py`) только хранится и в расчётах не
участвует.

### Статусы документов

* заказ: `new` → `shipped` → `returned`; `new` → `cancelled`;
* приход: `posted` → `reversed` (сторно возможно, только если товар прихода не
  расходовался);
* заказ поставщику: `open` → `closed`.

## Отчёты

Модуль отчёта определяет `COLUMNS`, `build(db, **opts)` (строки с «сырыми»
значениями) и `render(db, fmt, **opts)`. CSV-вывод использует ключи колонок и точку в
числах — на него завязаны выгрузки аналитиков, менять колонки существующих отчётов
нельзя. Реестр — `reports.REPORTS`, параметры командной строки для каждого отчёта —
`cli.REPORT_OPTIONS`.

## Мёртвый и устаревший код

* `old_valuation.py` — оценка по средней (схема 2), не используется;
* `legacy_xml.py` — выгрузка для закрытого сайта;
* `menu.py` — старое текстовое меню, новые операции туда не добавляются;
* `permissions.py`, `locking.py` — заготовки, нигде не подключены.

## Тесты

`tests/helpers.py` — стандартная база `make_db()` и запуск CLI в подпроцессе
(`run_cli`). Тесты не должны зависеть от текущей даты и от переменной окружения
`STOCKROOM_DB`.
